Register models¶

Implemented (RP-16A, RP-16B, RP-28B), Linux x86_64 inside Rack Free 2.6.6. A model’s widget is a Python module widget (below), or RackPy’s plain panel without one. Modules process audio with kernels, and plugin settings are in state.

Warning

Models and patches cannot create or enable laboratory modules. Python audio callbacks are refused in normal ModuleClass; use native kernels for audio. The explicitly enabled laboratory runs only offline on the main thread, never Rack’s engine or driver threads. Loading patch data never opts into executing Python callback code.

To start a plugin of your own, bin/rackpy-plugin creates a project, generates a module and its widget from an SVG panel, and builds a plugin directory from a RackPy bundle: see the plugin template and, for a module with sound, the oscillator. The configuration, state and events and menus examples show a module’s controls, bypass and presets, its events and saved state, and its context menu.

A Rack plugin offers models: the entries in Rack’s module browser. Each model makes modules, the instances in a patch. In a RackPy plugin, the trusted entry module (named by entry in rackpy-loader.json) adds its models while Rack loads the plugin:

register_models.py · Runs inside Rack; tested against the built plugin¶
import rackpy.assets
from rackpy.engine import Module
from rackpy.plugin import ModuleClass, on_destroy, plugin
from rackpy.types import JSON


def controls(module: Module) -> None:
    module.config(num_params=1, num_inputs=1, num_outputs=1)
    module.config_param(0, 0, 2, 1, "Level")
    module.config_input(0, "In")
    module.config_output(0, "Out")


class Notes(ModuleClass):
    SCHEMA = 1

    def configure(self) -> None:
        self.module.config(num_params=0, num_inputs=0, num_outputs=0)
        self.text = ""

    def to_json(self) -> object:
        return {"schema": self.SCHEMA, "text": self.text}

    def from_json(self, data: JSON) -> None:
        text = data.get("text") if isinstance(data, dict) else None
        if isinstance(text, str):  # patch data is untrusted: keep only what you expect
            self.text = text

    def on_reset(self, event: Module.ResetEvent) -> None:  # Initialize, after Rack reset the parameters
        self.text = ""


plugin.add_model("PyControls", controls, hp=4)
plugin.add_model("PyNotes", Notes, hp=8)
assert [model.slug for model in plugin.raw.models] == ["PyControls", "PyNotes"]
assert rackpy.assets.plugin("plugin.json").is_file()


@on_destroy
def goodbye() -> None:
    pass  # Python-only cleanup; Rack's objects are gone by now

plugin.add_model(slug, module, hp=...) takes the model’s slug and how to build its modules, either way shown above:

  • a module factory, the same constructor callback you give Module.create (module construction): configure the module there and set its state handlers;

  • a ModuleClass subclass: Rack’s module gets one instance, which configure() sets up through self.module, and whose to_json() and from_json() are the module’s state handlers. The instance lives exactly as long as Rack’s module, so keep per-module Python state on it.

Rack builds a module every time it needs one, on its main thread: when you add it from the browser, when a patch loads, when you undo a deletion or duplicate a module. Do not start threads or touch files there.

Give a model a module widget¶

add_model’s widget= is the model’s module widget: a rackpy.raw.app.ModuleWidget subclass, or a function, that Rack calls with the module, or None for its browser’s preview. Build the panel and controls in it, as a C++ module widget’s constructor does:

module_widget.py · Runs inside Rack; tested against the built plugin¶
from rackpy import raw
from rackpy.engine import Module
from rackpy.plugin import plugin
from rackpy.raw import app
from rackpy.raw.math import Vec
from rackpy.raw.window import Svg

# Original artwork, inline: a 4 HP panel and a jack.
PANEL = (
    '<svg xmlns="http://www.w3.org/2000/svg" width="60" height="380">'
    '<rect width="60" height="380" fill="#283038"/><rect x="6" y="6" width="48" height="14" fill="#48525e"/></svg>'
)
JACK = (
    '<svg xmlns="http://www.w3.org/2000/svg" width="24" height="24">'
    '<circle cx="12" cy="12" r="11" fill="#aab2bc"/><circle cx="12" cy="12" r="5" fill="#0e1216"/></svg>'
)


def svg(text: str) -> Svg:
    image = Svg()
    image.load_string(text)
    return image


def blink(module: Module) -> None:
    module.config(1, 0, 1, 1)
    module.config_param(0, 0.1, 10, 1, "Rate", " Hz")
    module.config_output(0, "Pulse")
    module.config_light(0, "Blink")


class Jack(app.SvgPort):
    def __init__(self) -> None:
        super().__init__()
        self.set_svg(svg(JACK))


class Rate(app.Knob):
    def __init__(self) -> None:
        super().__init__()
        self.box.size = Vec(26, 26)


class Lamp(app.ModuleLightWidget):
    def __init__(self) -> None:
        super().__init__()
        self.box.size = Vec(8, 8)
        self.add_base_color(raw.nanovg.rgb(255, 196, 64))


class BlinkWidget(app.ModuleWidget):
    """Rack calls this with the module, or None for its module browser's preview."""

    def __init__(self, module: Module | None) -> None:
        super().__init__()
        self.set_module(module)  # first, as Rack's module widgets do
        self.set_panel(svg(PANEL))
        self.add_param(raw.create_param_centered(Rate, Vec(30, 90), module, 0))
        self.add_child(raw.create_light_centered(Lamp, Vec(30, 150), module, 0))
        self.add_output(raw.create_output_centered(Jack, Vec(30, 300), module, 0))


plugin.add_model("PyBlink", blink, widget=BlinkWidget)

Call self.set_module(module) first. The widget owns its module from then on, and its ports connect cables (module widgets). Without widget=, the model gets a plain panel hp wide.

Module events¶

A ModuleClass may also override Rack’s module events: on_add, on_remove, on_bypass, on_un_bypass, on_port_change, on_reset, on_randomize and on_save, each called with Rack’s event, as on_reset above is. A factory function installs the same handlers with module.set_event_handlers(on_reset=..., ...) in the constructor callback. Only the events you handle cost anything.

They run on Rack’s main thread after Rack’s own behaviour; by the time on_reset runs, Rack has already reset the parameters. For all but on_save, Rack has stopped audio while the handler runs, so keep them short: RackPy records slow_exclusive_callback in rackpy.runtime.diagnostics() when one takes over 1 ms, and calls that need Rack’s engine lock raise EngineLockError there. Errors are logged and contained. Rack’s sample-rate and master events can arrive on audio threads, so Python cannot handle them (RP-22’s laboratory); kernels get the sample rate natively (processing audio).

plugin.json lists the same models¶

Rack reads a plugin’s models from two places and rejects the plugin unless they match: what init() registers and the "modules" list in plugin.json, which also gives each model its name, description and tags:

"modules": [
  {"slug": "PyControls", "name": "Controls", "description": "A level control", "tags": ["Utility"]},
  {"slug": "PyNotes", "name": "Notes", "description": "Text saved with the patch", "tags": ["Utility"]}
]

RackPy checks this when the entry module returns. If a slug is listed but not added, or added but not listed, RackPy adds no model, shuts its Python down and writes the difference to Rack’s log (RackPy host initialization failed (4): ... listed but not added: ...). Rack then skips the plugin and keeps running. The same happens if the entry module raises (failed (3)): models it added before the error are dropped.

Models can be added only during that import. add_model raises OwnershipError later, ValueError for a slug that is not valid (rackpy.raw.plugin.is_slug_valid: letters, digits, - and _) or already added, and TypeError for a factory that is not callable.

When the entry module fails¶

Rack’s log (log.txt in the Rack user folder) gets the traceback and a line saying what failed, RackPy host initialization failed (3): .... An entry module that does not exist is named as such, and so is a module it imports that the plugin does not ship: RackPy runs only the plugin’s own files (pythonpath/) and Python’s standard library, never packages installed elsewhere on the computer.

The standard library comes first. A plugin file or folder named like a standard module, such as json.py or random/, is never imported: Python finds the standard one, for RackPy and for every other import. Rack’s log names any such file as the plugin loads (“named like part of Python’s standard library”); rename it.

When a module factory fails¶

Rack expects a module every time it asks for one and cannot handle a failure, so RackPy never lets one reach it. If the factory raises, the error goes to Rack’s log and rackpy.runtime.diagnostics(), and Rack gets a placeholder: a module without controls, on a panel labelled “(failed)”. It keeps everything the patch saved for that module and writes it back unchanged, so saving the patch does not lose the module’s state. Fix the script and reload the patch to get the real module back.

Files and shutdown¶

rackpy.assets.plugin("res/table.json") is a file in the plugin’s own folder, rackpy.assets.system(...) one in Rack’s, both read-only, and rackpy.assets.user(...) one in Rack’s user folder, which you may write. They return pathlib.Path. Files that belong to one module in one patch go in its patch storage instead.

When Rack exits it first closes its context, which runs rackpy.runtime.on_context_closing callbacks while Rack’s objects still work, and later calls the plugin’s destroy(), which runs rackpy.plugin.on_destroy callbacks. By then every handle is stale, so use on_destroy for Python-only cleanup.

Threads and lifetime¶

Plugins and models belong to Rack for its whole run; the Python objects (rackpy.raw.plugin.Plugin and Model) are handles to them, used on the main thread only. A model added from Python keeps its factory until Rack shuts down, and RackPy releases it before Python stops.
