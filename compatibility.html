Compatibility baseline¶

RP-02 record, verified 2026-10-21. This page pins what RackPy targets and records what has been checked so far. Compatibility with a running Rack host has not been tested. Nothing here says a RackPy runtime exists.

Machine-readable pins are in upstream/versions.json. Recorded digests, the include closure and a preliminary declaration survey are in tests/fixtures/sdk-provenance.json. Both are checked by bin/rack-sdk.

Rack baseline: keep 2.6.6¶

Fact

Evidence

v2.6.6 is the newest v2 tag

git ls-remote --tags https://github.com/VCVRack/Rack.git

The tag is lightweight and names commit 061ccf63c1758599396ac1bb10d47345d9d34076

gh api repos/VCVRack/Rack/git/ref/tags/v2.6.6

refs/heads/v2 and HEAD also pointed at that commit on 2026-10-21

git ls-remote https://github.com/VCVRack/Rack.git refs/heads/v2 HEAD

SDK headers equal the source tree’s include/ at that commit

diff -r of a shallow checkout against the extracted lin-x64 SDK: no differences

No GitHub releases exist; binaries come from vcvrack.com

gh release list -R VCVRack/Rack is empty

Decision: keep the research baseline. RackPy targets the commit, not the mutable v2 branch. A new Rack release means an inventory diff and owner-visible notes (see coverage), not a version edit.

No SDK exists for lin-arm64 or win-arm64. Both URLs return a 404 page.

What differs between the four archives:

  • include/ is byte-identical on every platform. The macOS archives also contain a Finder .DS_Store, which the tree digests exclude.

  • dep/include/ differs only in openssl/configuration.h. OpenSSL headers are not reachable from rack.hpp.

  • arch.mk, compile.mk, plugin.mk, dep.mk and helper.py are identical.

  • Only the platform library differs.

So the declaration text is the same everywhere. Platform differences come from preprocessor branches and system headers, listed under platform branches.

Official cross toolchain: rack-plugin-toolchain branch v2 at 4fd13187, pinned to SDK 2.6.6. It builds crosstool-ng x86_64-ubuntu16.04-linux-gnu, mingw-w64 v10.0.0 and osxcross with clang 20.1.1 and the macOS 12.3 SDK. RP-08 built the Linux toolchain with bin/rack-toolchain build (GCC 15.1.0, sysroot glibc 2.23); RP-41 built its Windows toolchain (--target win-x64, mingw-w64 v10, msvcrt) for local cross builds, while CI builds Windows natively with MSYS2’s MinGW-w64 GCC. The macOS toolchain has not been built: macOS builds use Xcode’s (RP-40).

Selected toolchains.

  • Development and validation on Linux x64: the host GCC, driven by the SDK’s own plugin.mk so that the flags are Rack’s. RP-02 validated the rack.hpp-only probe this way.

  • Distributable artifacts: the official toolchain above. For Linux, RP-08 pinned it (commit, Makefile SHA-256, a digest-pinned Docker build image), built it and checked it: the skeleton built with it needs at most GLIBC_2.14, and the bundled libpython needs GLIBC_2.17 (ADR 005).

Findings that constrain later tasks¶

  1. A host-toolchain Linux build is not distributable. The probe built with the host GCC needs GLIBC_2.35; libRack itself needs only GLIBC_2.17. Linux release artifacts need the official toolchain or an equivalent old-glibc sysroot. Host builds are fine for development and tests. RP-08 builds with the official toolchain in CI and checks the floor with bin/rackpy-dev inspect --max-glibc 2.23. RP-39’s release candidates (bin/rackpy-release build) are built this way, and run on clean Ubuntu 16.04 (glibc 2.23) and 20.04 containers (install on Linux).

  2. Windows mixes C runtimes unless proven otherwise. Plugins link against a MinGW import library. python.org CPython is built with MSVC. RP-41 chose: RackPy’s DLLs are built with MinGW-w64 GCC on msvcrt, as Rack is, and the bundled CPython (python-build-standalone, MSVC and the Universal C Runtime) is used only through its C API, with no FILE*, heap block or errno crossing between the two runtimes. bin/rackpy-release build refuses a RackPy DLL that imports the Universal C Runtime (install on Windows). One consequence: file descriptors 0 to 2 are separate in each runtime over the same console handles, so Python code that closes them closes Rack’s.

  3. Headers accept newer C++. rack.hpp parses with GCC 16.2.1 and clang 23.1.3 under -std=c++17, c++20 and c++23 with no errors. Under C++20, GCC warns about implicit this capture in helpers.hpp. Header parsing does not prove ABI compatibility with a C++11-built libRack. RP-04 must check that before a C++17 binding library such as nanobind is chosen.

  4. SIMD is platform-conditional. simd/common.hpp uses <nmmintrin.h> when __SSE4_2__ is defined and SIMDe emulation otherwise. The x64 flags select the native path; arm64 uses SIMDe. Binding and tests for simd:: must run on both. (RP-20)

  5. Clang needs one SDK flag changed. -fno-gnu-unique is GCC-only, and the SDK’s -Wno-vla-extension does not silence clang 23’s -Wvla-cxx-extension in dsp/ode.hpp. The libclang inventory (RP-05) has to use adjusted flags and record them.

Reproduce¶

bin/rack-sdk fetch --fresh   # download all four SDKs into new empty dirs; check SHA-256
bin/rack-sdk verify          # archive, header-tree and library digests
bin/rack-sdk closure         # Linux x64 rack.hpp include closure versus the fixture
bin/rack-sdk survey          # preliminary declaration survey versus the fixture
bin/rack-sdk probe           # build tests/fixtures/sdk-probe with the SDK's plugin.mk
bin/rack-sdk environment     # host facts to record with a run

The script is a PEP 723 uv script and runs without a project environment. closure needs GCC, survey needs clang, and probe needs GNU Make, GCC, jq (the SDK’s plugin.mk reads plugin.json with it) and binutils. Downloads go to $XDG_CACHE_HOME/rackpy/sdk, or --cache DIR. Pass --write to closure or survey to regenerate the fixture, and review the diff before committing it.

Results on the planning machine¶

CachyOS, Linux 7.2.11, x86_64, glibc 2.44, GCC 16.2.1, clang 23.1.3, GNU Make 4.4.1, uv-managed CPython 3.14.2 for the script.

  • verify: all four archives, header trees and libraries matched from an empty cache. A changed byte in an extracted header made verify and closure fail.

  • probe: built with no warnings, exports init, needs libRack.so, libm and libc, and has RUNPATH /tmp/Rack2. It needs at most GLIBC_2.35.

  • closure: 112 Rack headers and 13 dependency headers reached; 12 shipped Rack headers not reached.

  • survey: deterministic across repeated runs. Its counts are navigation data, not coverage. See coverage.
