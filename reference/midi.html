MIDI¶

rackpy.raw.midi is Rack’s rack::midi: MIDI messages, Rack’s MIDI drivers and devices, and MIDI ports that Python owns. Implemented (RP-29A, RP-29C), Linux x86_64 inside Rack Free 2.6.6 (see the coverage report).

midi_loopback.py · Runs inside Rack; tested against the built plugin¶
from rackpy.raw import midi

LOOPBACK = -12  # Rack's Loopback MIDI driver: what goes out on device N comes in on device N


class NoteLog(midi.Input):
    """Collects the notes that arrive. RackPy calls on_message on the UI thread, not the MIDI thread."""

    def __init__(self) -> None:
        super().__init__()
        self.notes: list[int] = []

    def on_message(self, message: midi.Message) -> None:
        if message.get_status() == 0x9 and message.get_value() > 0:  # note on
            self.notes.append(message.get_note())


def open_loopback(device_id: int) -> tuple[midi.Output, NoteLog]:
    """Call from Rack's UI thread: an output and a NoteLog on one loopback device."""
    out, log = midi.Output(), NoteLog()
    for port in (out, log):
        port.set_driver_id(LOOPBACK)
        port.set_device_id(device_id)
    return out, log


def note_on(note: int, velocity: int = 100) -> midi.Message:
    message = midi.Message()
    message.set_status(0x9)
    message.set_note(note)
    message.set_value(velocity)
    return message

Messages¶

A Message is a value: bytes (three zeros at first, as a list of 0 to 255) and frame, the engine frame it belongs to (-1: now). The accessors are Rack’s:

  • get_status/set_status and get_channel/set_channel read and write the two halves of the first byte.

  • get_note/set_note and get_value/set_value read and write the next two bytes. The setters mask to 7 bits.

  • A missing byte reads as 0, and setting it does nothing (set_size changes the size).

  • to_string() is the bytes in hex.

Rack’s drivers¶

get_driver_ids() lists Rack’s MIDI drivers, and get_driver(driver_id) returns one as a Driver, a view by ID. Python never deletes a driver: Rack deletes every one, its own and Python’s, in its midi::destroy() as it quits, after closing its context and before the plugins’ destroy(), so a destroy callback finds a PythonDriver handle stale; a test in Rack checks this. Rack Free has these:

  • Loopback (-12), whose 16 devices pass what is sent on device N to the inputs on device N.

  • Computer keyboard/mouse.

  • Gamepad.

  • RtMidi’s, such as ALSA and JACK, depending on the machine.

A driver lists its input and output devices and their names and defaults. subscribe_input(device_id, port) and subscribe_output make a Python port a subscriber of a device, apart from the port’s own device. RackPy undoes such a subscription when the port dies, and unsubscribe_* takes back only the subscriptions Python made. A port holds each device once: Rack’s subscriber sets ignore a second subscription, so subscribing (through the driver or the device) to a device the port already holds is refused, and when set_device_id makes a subscribed device the port’s own, that subscription becomes the port’s device. Unsubscribing the port’s own device is refused: set_device_id(-1) leaves it.

Ports¶

Input(), InputQueue() and Output() are Rack’s ports, owned by Python, on the main thread in Rack’s live UI. They need Rack’s engine to timestamp messages, so making one at plugin start-up raises ContextError. As in Rack, a new port takes Rack’s first driver and its default device. A port has Rack’s methods:

  • set_driver_id falls back to Rack’s first driver for an unknown ID, then takes its default device.

  • set_device_id takes a device, and -1 means none.

  • get_driver and get_driver_id return the port’s driver and its ID; get_device_id returns its device’s ID (-1: none) and get_device the device’s view, or None. The properties driver, driver_id, device_id and device are the same (driver is None for a driver that Rack’s list does not hold, such as a laboratory driver), and an Input’s input_device and an Output’s output_device are Rack’s typed fields: an InputDevice or an OutputDevice view.

  • get_device_ids, get_device_name, get_channels, get_channel_name, to_json, and from_json, which finds the saved device by name.

  • channel is an input’s channel filter, or the channel an output sets on each message (-1: all, or leave it).

  • reset() is Rack’s: set_driver_id(-1), which (as -1 is no driver) falls back to Rack’s first driver and that driver’s default device, then the port’s default channel: -1 (all) for an input and 0 for an output.

  • The read-only context property is the Rack context the port was made in, as Rack’s Port::context field.

get_device_ids, get_default_device_id, set_device_id, get_device_name and get_channels are Rack’s virtuals. A Python Input or Output subclass may override them, and Rack’s menus and its set_driver_id then call the override on the UI thread.

  • Input. Rack delivers messages on the MIDI driver’s thread, or, for the Loopback driver, on whichever thread sends, often an engine thread. Python never runs there. The native port copies each message into a preallocated queue of up to 1024 messages and 64 KiB of total message bytes; a single message may use at most 64 KiB. RackPy calls the subclass’s on_message(message) on the UI thread at its next step. The queue never blocks or allocates on the sending thread: a message that finds it busy, full, or over either byte limit is dropped and counted in dropped. An unset frame is set from Rack’s engine timing, as Rack does.

  • InputQueue is Rack’s queue port. It keeps up to 8192 messages in frame order, and try_pop(max_frame) returns the next one due, or None. A Python-owned module can attach an empty, disconnected InputQueue using set_midi_input(index, queue) (indices 0–3), then connect the port to a device. Its native queue delivers messages to a compatible kernel at their engine frames; try_pop() and size() raise OwnershipError while it is attached. set_midi_input(index, None) detaches it while the module is Python-owned. For memory safety, a port permits at most 32 attachments over its lifetime. module.midi_input_stats(index) reports received, delivered, full-queue and long-message drops and the waiting count after the last frame. Messages longer than three bytes are dropped, including SysEx.

  • Output.send_message(message) sends to the port’s device, setting the port’s channel unless it is -1.

Rack’s drivers outlive its context but not RackPy’s interpreter. Every Python port therefore gives up its devices when Rack’s context closes, and is stale from then on. A port Python drops is deleted on the main thread.

Devices¶

A device belongs to its driver; Rack’s RtMidi driver deletes one when its last port leaves. Python reaches a device only through the port that holds it (port.device, input_device, output_device, or a driver’s subscribe_*), and the view goes stale once the port lets go.

  • get_name() is the device’s name.

  • subscribed lists the device’s subscribers: Python’s own ports, and read-only PortViews of the others, such as modules’ ports.

  • InputDevice.on_message(message) delivers a message to the subscribers, as the driver does when one arrives.

  • OutputDevice.send_message(message) sends it as it is, without applying any channel.

  • subscribe(port) and unsubscribe(port) are Rack’s lower-level calls, which Rack says are not meant for plugins: a subscribed input hears the device as well as its own, until it unsubscribes. unsubscribe takes back only a subscription that subscribe made, and raises OwnershipError otherwise (for the port’s own device, say). RackPy undoes them with the port, as it does a driver’s.

Python drivers and devices¶

Warning

Native configured answers and queued notifications below do not preserve synchronous Python override semantics. Synchronous Python overrides of the driver, device and input virtuals exist only in the laboratory (rackpy.laboratory.MidiDriver, MidiInputDevice, MidiOutputDevice, MidiInput, MidiInputQueue), offline, explicitly enabled, on the main thread, never on Rack’s engine or MIDI driver threads; see the callback inventory.

Python implements a MIDI driver as a natively configured PythonDriver (RP-29C), whose calls native code answers:

  • add_input_device(name) returns a PythonInputDevice. Its push_message(message) is Rack’s InputDevice::onMessage, as a driver calls it when a message arrives: every subscribed input gets it, filtered by channel and timestamped by Rack’s engine if its frame is unset.

  • add_output_device(name) returns a PythonOutputDevice. Rack’s ports send to it from engine threads (modules’ process()), so it only queues each message, without blocking, in a queue of 1024 that counts drops in dropped. take_sent() returns the queued messages, in order, on the main thread. A Python sendMessage override exists only offline, in the laboratory.

  • remove_input_device/remove_output_device unplug a device. Rack’s lists no longer show it, the ports that hold it keep it until they move, and it is deleted when the last one leaves: its alive is then false. A removed input refuses pushes.

  • add_driver(driver_id, driver) gives the driver to Rack, which owns it until it quits. Taken IDs are refused.

The rackpy.midi facade builds messages (note_on, note_off, control_change, message, with range checks), finds drivers by name (drivers, find_driver), opens ports by driver and device name (open_input, open_output), and makes a virtual driver with its devices (virtual_driver). Duplicate driver or device names raise LookupError rather than selecting one silently; use IDs to disambiguate. drivers() also raises when its name map would lose a duplicate. Raw ID enumeration remains available.
