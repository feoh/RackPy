Values: math, colours, quantities and common helpers¶

Family 1 of the SDK surface: math.hpp, color.hpp, Quantity.hpp, common.hpp and arch.hpp (RP-12). The string, random, logger, mutex and weak-pointer utilities in the same family belong to the services task (RP-30).

Every function here runs Rack’s own C++ code, compiled with the SDK’s flags. tests/values replays more than 7,000 cases from a compiled C++ reference through these bindings, inside Rack, and requires the results to be identical bit for bit, so nothing here is a Python re-implementation that could drift from Rack.

The low-level names are in rackpy.raw (C++ namespace for namespace: rack::math is rackpy.raw.math); rackpy.math and rackpy.types are the tidy imports for everyday use.

Numbers cross as C++ numbers¶

  • A Python float becomes a C++ float: it is rounded to 32 bits, and a magnitude beyond the float range becomes ±inf, exactly as a C++ cast does. rackpy.math.crossfade(0.1, 0.1, 0) is 0.10000000149011612.

  • A Python int becomes the C++ integer type the function takes. A value that does not fit raises OverflowError; it never wraps silently and never falls through to a float overload.

  • NaN and infinities pass through with Rack’s semantics: rescale over an empty range divides by zero, giving ±inf (or NaN when x is the range’s start), as Rack’s does.

  • The sign of a zero is not part of Rack’s semantics. Rack and RackPy are compiled with -funsafe-math-optimizations, which implies -fno-signed-zeros, so a function may return 0.0 or -0.0 for the same input depending on the compiler and call site: clamp(-0.0) is 0.0 from one build and -0.0 from another. Compare results with ==, which treats them as equal. normalize_zero is the exception: Rack compiles it to keep signed zeros, and it always returns +0.0.

  • Denormals are flushed to zero inside Rack. Rack’s main() sets the CPU’s flush-to-zero and denormals-are-zero modes (system::resetFpuFlags()), and threads inherit them, so in a Rack process all float arithmetic, including plain Python float arithmetic, treats subnormal numbers as zero: math.ldexp(1.0, -1070) is 0.0 inside Rack and about 7.9e-323 outside it. The C++ reference test runs in the same mode.

Scalar functions¶

clamp, clamp_safe, euc_mod, sgn and the other helpers keep every C++ overload. Python picks one by argument type: all-int arguments reach the int overload, anything else the float one, so clamp(15, 0, 10) is the integer 10 and clamp(1.5) uses the float defaults 0 and 1.

Vec¶

Vec(x, y) is a 2D vector of C++ floats with Rack’s methods (plus, norm, rotate, …; mult and div take a Vec or a float, as their two C++ overloads do) and Rack’s operators: +, -, * and / with a Vec or a float, unary + and -, == and !=, and the in-place forms, which change the Vec itself. v[0] is x; every other integer index reads or writes y, matching Rack’s operator[] (including negative and out-of-range indices).

A Vec is a mutable value: assigning it or passing it to a function copies it, as in C++, and copy.copy makes an independent copy. Being mutable, it is not hashable.

Rect¶

Rect(pos, size) or Rect(x, y, width, height) includes its left and top edges but not its right and bottom ones. Rect.inf() is the whole plane. It has Rack’s methods, which return new values: the static constructors from_min_max and from_corners; the getters (get_left, …, get_center, get_top_left, get_top_right, get_bottom_left, get_bottom_right); contains, which takes a Vec or a Rect, intersects and equals; clamp, nudge, expand, intersect, zero_pos, grow, shrink and interpolate; and Rack’s aliases is_containing, is_intersecting and is_equal. == and != are Rack’s operators. The facade adds read-only properties (left, right, top, bottom, width, height, center) over Rack’s getters.

Copies and views¶

The one rule that matters: a field read from a Rack object is a view of that field, not a copy.

r = Rect(1, 2, 3, 4)
r.pos.x = 10      # changes r: r.pos is a view of r's field
p = r.pos         # still a view; p keeps r alive
p = copy.copy(r.pos)   # an independent Vec
r.pos = Vec(7, 8) # assignment copies the new value into r

Methods and operators return new values. RackPy never hands out a copy where C++ returns a reference: when a later family binds a widget’s box, writing widget.box.pos.x will move the widget, exactly as in C++.

Colours¶

NVGcolor(r, g, b, a=1.0) (also rackpy.types.Color) is nanovg’s colour, which Rack passes by value everywhere. It is therefore an immutable value: its components are read-only and it is hashable. Names such as rackpy.raw.color.RED and WHITE_TRANSPARENT are conventional module-level constants; Python allows rebinding a module attribute, but that does not mutate the original value or Rack’s C++ constant. The rackpy.raw.color functions are Rack’s: lerp, screen, alpha, mult (by a colour or a float), and so on.

from_hex_string behaves as Rack’s implementation does, which is not what its header says. color.hpp documents “returns WHITE on error”, but the code reads the text with sscanf and returns whatever it parsed: opaque black for text it cannot read at all, and a partial colour for partial input ("#ff" is opaque red). It never raises. RackPy follows the implementation, and the C++ reference test checks that it does.

Quantity¶

rackpy.raw.Quantity is rack::Quantity, the value-with-bounds-and-labels that knobs and sliders display. What a Python subclass may override depends on where Rack calls each method (callback matrix):

When Rack calls a plain quantity’s value method off the main thread, RackPy never invokes Python: it uses the C++ base answer and records one bounded refusal diagnostic per object. The result may therefore differ from the Python override. Do not use such overrides for production audio. Parameter quantities can use Python value overrides only in the separately enabled callback laboratory.

rackpy.types.ValueQuantity keeps its value, bounds and default natively, so Rack can read the base values from any thread. Like Rack’s ParamQuantity, it clamps a new value to its bounds with clamp_safe. Because fmin(NaN, max) is max, a NaN becomes the maximum. set_display_value_string accepts Rack’s formula language ("c4", "1+1", "dbtogain(-6)") and leaves the value unchanged if the text does not parse.

When Rack calls a Python override and it raises, the error is caught at the boundary, logged and recorded as a callback_raised diagnostic, and Rack’s default answers instead. When your own Python code calls the method, the error reaches you as usual.

Exception¶

rackpy.raw.Exception is rack::Exception. Rack’s C++ exceptions arrive in Python as this type, a RuntimeError, with msg and what() giving the message. The printf-style constructor is Exception.printf(format, *args), which uses Rack’s string.f formatter with checked arguments, so printf("%lld ports", 3) reads 3 ports and %a formats a hexadecimal float. Like string.f, it refuses %n and %p and embedded NULs in %s arguments; the format itself is a C string and ends at its first NUL.

Files by UTF-8 name: fopen_u8 (Windows only)¶

On Windows, the C runtime’s fopen reads a file name in the ANSI code page, so common.hpp declares fopen_u8, which converts the UTF-8 name and mode to UTF-16 and calls _wfopen, and #defines fopen to it. RackPy maps both: rackpy.raw.fopen_u8(filename, mode) and rackpy.raw.macros.fopen, the same function. On Linux and macOS neither name exists, as in C++.

It returns a rackpy.raw.CFile, which owns the FILE*: read(size=-1) (fread; b'' at the end), write(data) (fwrite of all of a bytes-like object), seek(offset, whence=0) and tell() (64-bit), flush() and close(). A with block closes it, and so does Python when it frees the object; closing twice does nothing, and any other call on a closed file raises ValueError. Where C returns NULL or a call fails, it raises OSError (FileNotFoundError and so on) with the C runtime’s errno, read where Rack’s _wfopen set it, in msvcrt, and passed to Python as a number. A file name or mode with a NUL character raises ValueError, as C would stop at it. Calls hold the GIL, so a close cannot race a read; it is file I/O, not for the audio thread.

JSON¶

Rack’s state and settings APIs exchange jansson json_t. RackPy never hands Python a json_t; it converts at the boundary, in both directions, with one policy (native/runtime/json.cpp), described by rackpy.types.JSON:

  • null, booleans, integers, reals, strings, arrays and objects become None, bool, int, float, str, list and dict; tuples are accepted as arrays.

  • Integers must fit jansson’s 64-bit json_int_t (OverflowError otherwise).

  • NaN and infinities raise ValueError: JSON cannot represent them.

  • Object keys must be str (TypeError). Neither keys nor strings may contain NUL characters (ValueError): jansson writes NUL as \u0000, but Rack loads patches, presets and the clipboard without JSON_ALLOW_NUL, so it would refuse the whole file (RP-15C).

  • From json_t, strings that are not valid UTF-8 raise UnicodeDecodeError. jansson’s own loader refuses them; only a plugin’s json_string_nocheck can make one.

  • Anything nested more than 64 levels deep, which includes a list that contains itself, raises ValueError.

Later families use this for dataToJson, paramsFromJson, plugin settings and so on (RP-15).

Buffers and opaque handles (design for later families)¶

Two more boundary policies, designed here and implemented where they first appear:

  • Buffers. Native arrays (a port’s 16 voltages, a DSP block) reach Python through the buffer protocol only from an object that owns or keeps alive the storage: a snapshot copy, or a view that is valid only inside the callback that provided it and raises afterwards (ADR 003, decisions 8 and 10). RP-13 implements port voltage views.

  • Opaque handles. Pointers Python must not dereference (GLFWwindow*, NVGcontext*, Context::patch) become handle objects that support identity and a null check and nothing else, never an integer address (coverage policies 4, 8 and 13): rackpy.raw.window.NativeHandle (drawing and the window).
