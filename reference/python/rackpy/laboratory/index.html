rackpy.laboratory¶

The callback laboratory: Python overrides of a module’s audio-thread callbacks, run offline.

Rack calls a module’s process once per sample on its engine threads, where RackPy never runs Python: production modules process audio with native kernels (rackpy.dsp.kernel). The laboratory runs Python there anyway, for experiments and tests. A laboratory module (a ModuleClass) runs only on a Bench, an offline host that steps RackPy modules from Python on Rack’s main thread the way Rack’s engine would. Rack’s engine never runs a laboratory module, a patch cannot create one, and nothing here is real-time audio. See Callbacks and the laboratory in the explanations.

The laboratory’s audio and MIDI drivers and devices (AudioDriver, MidiDriver, …) do the same for the driver virtuals that Rack calls on its audio and MIDI driver threads: Rack never lists them, so only ports you make and connect reach them, on the main thread.

Trusted code must call enable() first. Available inside Rack only.

rackpy.laboratory.MidiOutputDevice¶

A MIDI output device whose send_message and get_name a subclass overrides; device.connect(output) points a rackpy.raw.midi.Output you made at it, so Rack’s Output::sendMessage reaches the override. A MidiDriver can also hold it (add_output_device).

rackpy.laboratory.AudioDriver¶

rack::audio::Driver whose every virtual a subclass may override, offline.

driver.connect(port) points a rackpy.raw.audio.Port you made at it, repeating what Rack’s Port::setDriverId does for a driver Rack lists (Rack never lists a laboratory driver): the port leaves its device, takes this driver, then subscribes to get_default_device_id()’s device. Rack’s own port methods then call the driver’s get_name, get_device_ids, get_device_name, get_device_num_inputs, get_device_num_outputs, subscribe and unsubscribe synchronously, and an override’s error reaches the caller of the port method. super() answers from the devices given to add_device, which the driver keeps; subscribe must return one of them or None. Main thread; creating one needs enable(). Its native part is destroyed on the main thread only: dropped on another thread, at the next UI step.

rackpy.laboratory.AudioDevice¶

rack::audio::Device whose every virtual a subclass may override, offline.

Rack’s port methods (get_sample_rate, set_block_size, to_json, …) call the device of a port connected to an AudioDriver synchronously; super() answers with the configured values (name, num_inputs, sample_rate, …), as a rackpy.raw.audio.PythonDevice does. Creating one needs enable().

rackpy.laboratory.MidiDriver¶

rack::midi::Driver whose every virtual a subclass may override, offline.

driver.connect(port) points a rackpy.raw.midi port you made at it, as Rack’s Port::setDriverId does for a driver it lists. Rack’s own port methods (set_device_id, get_device_ids, get_default_device_id, get_device_name) and Rack’s MIDI widgets then call the driver’s virtuals synchronously. super() answers from the MidiInputDevice and MidiOutputDevice objects added, which the driver keeps. Main thread; creating one needs enable(). Its native part is destroyed on the main thread only: dropped on another thread, at the next UI step.

rackpy.laboratory.MidiInputDevice¶

rack::midi::InputDevice whose get_name a subclass may override; push_message is Rack’s InputDevice::onMessage, which calls each subscribed input’s on_message. Creating one needs enable().

rackpy.laboratory.MidiInputQueue¶

rack::midi::InputQueue whose on_message a subclass may override, offline.

Rack’s InputDevice::onMessage calls it synchronously on the main thread (a MidiInputDevice’s push_message, Rack’s Loopback driver when Python sends); super().on_message(message) queues the message for try_pop, as Rack’s does. On Rack’s threads Python never runs and Rack’s queue takes the message. It is a rackpy.raw.midi.Input, but not a rackpy.raw.midi.InputQueue, which is final. Creating one needs enable() and Rack’s live context. As for MidiInput, no MIDI subscription may change while on_message runs.

class rackpy.laboratory.MidiInput¶

rack::midi::Input whose on_message runs synchronously, offline.

An ordinary rackpy.raw.midi.Input gets its messages queued, on the UI thread. A laboratory input’s on_message runs where Rack’s InputDevice::onMessage calls it on the main thread (a MidiInputDevice’s push_message, Rack’s Loopback driver when Python sends), and its error reaches that caller. On Rack’s MIDI driver threads Python never runs: the message is queued, as for an ordinary input. A native mark set by this constructor, after it checks enable(), gates the synchronous path. Needs Rack’s live context.

Rack is iterating the device’s subscribers while on_message runs, so until the call that delivered the message returns, changing any MIDI subscription (set_device_id, connect, removing a device, making a port, …) raises LaboratoryError, and objects dropped meanwhile are kept alive until then.

on_message(message: rackpy.raw.midi.Message) → None¶

Rack’s Input::onMessage: does nothing. A subclass receives each message here, an owned copy.

rackpy.laboratory.enable() → None¶

Allow laboratory modules and benches in this process, until disable().

Call it from trusted code: your plugin’s entry module or a test. Loading a patch never enables the laboratory. Rack’s log records that it was enabled. Main thread.

rackpy.laboratory.disable() → None¶

Refuse new laboratory modules and benches, and stepping existing benches, again.

rackpy.laboratory.enabled() → bool¶

Whether enable() was called (and disable() not since).

class rackpy.laboratory.ModuleClass(module: rackpy.engine.Module)¶

A module class whose every rack::engine::Module callback may be Python, on a laboratory Bench.

configure and the custom-data handlers to_json and from_json work as in rackpy.plugin.ModuleClass. The other methods are true overrides of Rack’s virtuals, called synchronously where Rack would call them and instead of Rack’s implementation: super() runs it (Rack’s, with RackPy’s lifecycle snapshot and data handlers), as in a C++ subclass of rack::engine::Module. So an on_reset() that does not call super() resets no parameters. Rack’s deprecated no-argument events have separate on_*_legacy override slots. Rack’s default modern events invoke them. Create one with create(), never through a model: Rack cannot create it.

classmethod create(model: rackpy.raw.plugin.Model | None = None) → Self¶

A new laboratory module of this class, configured; put instance.module on a Bench.

model only names the module in Rack’s JSON (Rack’s toJson and fromJson need one); Rack still never creates or runs it. Raises LaboratoryError unless the laboratory is enabled. Main thread.

class rackpy.laboratory.Quantity¶

rack::Quantity whose value and range methods a subclass may override, offline.

Rack’s own code that calls them (display values, reset, randomize, scaled values, the display string) reaches the override synchronously. Creating one needs enable(). Main thread.

class rackpy.laboratory.ParamQuantity¶

rack::engine::ParamQuantity whose value and range methods a subclass may override, offline.

Only a laboratory module takes one as config_param(..., quantity_type=...) or in its param_quantities: Rack’s engine can call an ordinary module’s quantities on its own threads. Rack’s code calling them (paramsToJson, reset, randomize, display) reaches the override synchronously. Creating one needs enable().

class rackpy.laboratory.SwitchQuantity¶

rack::engine::SwitchQuantity with laboratory value methods; see ParamQuantity.

rackpy.laboratory.MidiGenerator¶

MidiGenerator[N]: Rack’s dsp::MidiGenerator<N> whose on_message a subclass overrides, offline only.

Rack calls MidiGenerator::onMessage where a module generates MIDI, on its engine thread, so outside the laboratory RackPy’s generator only records the messages (take_messages()).
