Module construction and components¶

Implemented slices: RP-14A, built-in port/light metadata adapters (RP-14B1), checked built-in quantities (RP-14B2a), and borrowed quantity helpers / mutable switch-label views (RP-14B2b1), standalone metadata backreferences (RP-14B2b2), unattached and attached standalone quantities (RP-14B2b3/b4), and port/light and parameter-quantity class factories (RP-14B2b5/b6), and constructor-scoped raw module vectors (RP-14B2b7), module identity (RP-14C1) and engine ownership with engine smoothing (RP-14C2), Linux x86_64 inside Rack Free 2.6.6. Later slices add model registration, native kernels, lifecycle events, expanders and the offline Python callback laboratory (documented below). The laboratory is partial, with explicit callback blockers; see the coverage report for declaration-level status.

Warning

Python process overrides are laboratory only: explicitly enabled, offline, main-thread Bench execution, never Rack’s engine or driver threads. Normal ModuleClass refuses them at class definition, and a patch cannot create or enable a laboratory module. Use native kernels for audio; see callback paths and blockers.

Construction transaction¶

rackpy.engine.Module and rackpy.raw.engine.Module are the same native binding. Module.create(configure=None) constructs an owned, empty Rack module. When supplied, configure(module) runs synchronously on Rack’s main thread. Its return value is ignored; the factory returns the same Python handle it passed to the callback. Only that callback may call config, config_bypass, config_input, config_output, config_light, config_param, config_switch and config_button. These are construction operations, not engine commands.

config(num_params, num_inputs, num_outputs, num_lights=0) calls Rack’s implementation once. Counts must be nonnegative. Even config(0, 0, 0) consumes the one call: a second call raises OwnershipError before Rack’s assertion. Invalid counts are rejected before native configuration and can be corrected within the same callback. A failure partway through native allocation closes the module; it cannot be reused even if the callback catches the error.

The factory seals the module before returning it. Late configuration raises OwnershipError. Nested factories have independent construction scopes. Module.create() without a callback returns a sealed, empty module. Rack’s deprecated counting constructor Module(numParams, numInputs, numOutputs, numLights) is the overload Module.create(num_params, num_inputs, num_outputs, num_lights=0, configure=None): it emits DeprecationWarning, calls config first and then the optional callback, in the same transaction (so the callback cannot call config again).

Here is a runnable construction-only example. The documentation snippet tests run this exact file inside Rack:

module_construction.py · Runs inside Rack; tested against the built plugin¶
from rackpy.engine import Module


def wire(module: Module) -> None:
    module.config(num_params=1, num_inputs=1, num_outputs=1, num_lights=1)
    module.config_bypass(input_id=0, output_id=0)


module = Module.create(wire)
try:
    module.params[0].value = 0.5
    assert module.get_param(0) is module.params[0]
    # No engine owns this module: no ID yet, and never bypassed.
    assert module.id == -1 and not module.is_bypassed()
finally:
    module.close()

This does not add the module to Rack’s engine or install a DSP callback. A Python subclass or an attribute named process is not a DSP implementation. There is no Module virtual trampoline in this slice. The construction callback is never stored in the native module, and no audio path invokes it.

Identity and bypass state¶

module.id is Rack’s engine ID: -1 until an engine assigns one (Rack keeps IDs below 2^53 so they survive JSON, but any 64-bit integer is accepted, as in C++). It can be assigned only inside the constructor callback; get_id() is Rack’s getter. is_bypassed() is Rack’s query, and is False until Rack’s engine owns and bypasses the module (engine ownership; Rack’s own model factory, RP-16, is what hands a module to the engine). Both need the main thread. The model field and get_model() return the module’s rackpy.raw.plugin.Model, or None before Rack creates the module from one. Engine ownership, its deletion path and lifecycle events are the rest of RP-14C.

Component access¶

get_num_params/inputs/outputs/lights() and get_param/input/output/light(index) call Rack’s corresponding getters. Getter IDs must satisfy 0 <= index < count; invalid IDs raise IndexError instead of accessing an unchecked C++ vector.

params, inputs, outputs and lights are checked views of Rack’s vectors. They support length, iteration and integer indexing (including Python’s negative indices); slicing and named lookup are not supported. Setting a component’s value writes through to the actual Rack component. Repeated lookups of a live component preserve Python identity. Iteration snapshots the component handles, not their changing values. During construction they also take Rack’s raw vector edits (raw module vectors). For port channel and buffer rules, see Engine components.

Built-in port and light metadata¶

config_input(port_id, name=""), config_output(port_id, name="") and config_light(light_id, name="") configure built-in Rack metadata during construction. They return checked PortInfoView / LightInfoView adapters. IDs must be nonnegative and below the corresponding component count.

get_input_info(index), get_output_info(index) and get_light_info(index) return the same live adapters. Rack initializes input/output metadata in config; light slots are None until explicitly configured. input_infos, output_infos and light_infos are Components collections with negative indexing and iteration; during construction they take raw vector edits.

The adapters expose mutable name and description, get_name() and get_description(). A port also has get_full_name() (Rack appends “ input” or “ output”), type and port_id; a light has light_id. module returns the owning Python handle (or None). These identity fields can be assigned only during construction, and module only the owning module or None; the seal checks that they match the slot. All native metadata access requires the main thread, including null-slot lookups. alive is a liveness query and may be read from any thread.

Configuring the same slot again is permitted during construction. The old adapter immediately becomes stale; it cannot read a replacement that happens to reuse its address. Only that slot’s generation changes. Replacement prepares its native object, strings and generation before retiring the previous one, so a preparation exception leaves the old metadata intact. Closing the module, dropping its last handle, or failing construction invalidates every adapter, including retained collections. Views do not keep the module alive; explicitly retaining view.module does, just like retaining the original module handle. Once Rack’s engine owns the module, its handles no longer own it, so views stay valid while Rack keeps the module, even if the handle they came from is gone, and go stale when Rack deletes it.

module_metadata.py · Runs inside Rack; tested against the built plugin¶
from rackpy.engine import Module
from rackpy.raw.engine import LightInfo, PortInfo


def describe(module: Module) -> None:
    module.config(num_params=0, num_inputs=1, num_outputs=1, num_lights=1)
    module.config_input(0, "Pitch").description = "Pitch control in volts."
    module.config_output(0, "Signal")
    module.config_light(0, "Activity")


module = Module.create(describe)
standalone_port, standalone_light = PortInfo(), LightInfo()
standalone_port.module = standalone_light.module = module
assert standalone_port.module is standalone_light.module is module
try:
    info = module.get_input_info(0)
    assert info is module.input_infos[0]
    assert info.module is module
    assert info.get_full_name() == "Pitch input"
finally:
    module.close()
assert not info.alive
assert standalone_port.module is standalone_light.module is None
standalone_port.name = "Independent"
assert standalone_port.get_name() == "Independent"

Borrowed adapters are distinct from standalone, subclassable PortInfo / LightInfo. To put one of those classes into a slot, pass it as info_type (metadata class factories) or assign it to the slot (raw module vectors). Standalone metadata backreferences are documented in Engine components.

Metadata class factories¶

Rack’s configInput<TPortInfo>, configOutput<TPortInfo> and configLight<TLightInfo> construct a metadata object of the given class and put it in the slot. In Python, pass the class as info_type: config_input(port_id, name="", info_type=None), and the same for config_output and config_light. info_type must be PortInfo (or LightInfo for lights) or a Python subclass; anything else raises TypeError. Without info_type the built-in view described above is used.

RackPy calls info_type() with no arguments, on the main thread inside the constructor callback, as Rack’s new TPortInfo would. Your __init__ may set any field; then RackPy sets module, type, port_id (or light_id) and name exactly as Rack’s template does, so a description set in __init__ survives. The call returns that same Python object, and get_input_info, input_infos and the other getters return it again: the identity is preserved, with its class and attributes. An override of get_name or get_description is what Rack’s UI shows. When Rack calls it without Python holding the GIL, a raised exception is contained and Rack’s own answer is used instead.

metadata_factories.py · Runs inside Rack; tested against the built plugin¶
from rackpy.engine import Module
from rackpy.raw.engine import LightInfo, PortInfo


class VoltPort(PortInfo):
    """Rack shows this name in the port's tooltip."""

    def __init__(self) -> None:
        super().__init__()
        self.description = "Volts per octave."

    def get_name(self) -> str:
        return self.name + " (1V/oct)"


def describe(module: Module) -> None:
    module.config(num_params=0, num_inputs=1, num_outputs=0, num_lights=1)
    pitch = module.config_input(0, "Pitch", info_type=VoltPort)
    assert pitch.get_full_name() == "Pitch (1V/oct) input"
    module.config_light(0, "Activity", info_type=LightInfo)


module = Module.create(describe)
try:
    pitch = module.get_input_info(0)
    assert isinstance(pitch, VoltPort) and pitch is module.input_infos[0]
    assert pitch.module is module and pitch.get_description() == "Volts per octave."
finally:
    module.close()
# The slot owned the object; Python still has it, but it is stale now.
assert not pitch.alive

Ownership. The slot owns the object from then on and keeps its Python half alive. Its fields and methods are main-thread only, like a built-in view (ThreadError elsewhere); a standalone object keeps its any-thread fields. When the slot replaces it, or the module is closed, collected or its constructor fails, the object goes back to Python, alive becomes False and every field or method raises StaleHandleError, like a pointer Rack deleted. The Python object itself lives as long as you reference it. It may refer back to its module: a slot keeps its object alive, but the module’s handle reports that edge to Python’s garbage collector (RP-15A), so the cycle is collected once nothing else refers to it.

Errors are atomic. The constructor runs before anything changes: if it raises, or returns something other than a new instance of exactly info_type (a __new__ that returns another object), the slot keeps its old metadata. An object a slot already owns raises OwnershipError; one a slot has released raises StaleHandleError. The constructor may reenter the module, for example to configure the same slot; RackPy checks the construction phase and the ID again afterwards, and the outer call’s object then replaces the inner one.

These six records (the three templates and get_input_info, get_output_info, get_light_info) are implemented. Parameter quantities have their own class factories, described next.

Quantity class factories¶

Rack’s configParam<TParamQuantity>, configSwitch<TSwitchQuantity> and configButton<TSwitchQuantity> work the same way: pass the class as quantity_type. config_param and config_button take ParamQuantity or any subclass, including SwitchQuantity; config_switch needs SwitchQuantity or a subclass. RackPy checks Rack’s arguments (IDs, bounds, display coefficients) before it calls quantity_type(), then sets exactly the fields Rack’s template sets: module, param_id, the bounds and default, name, unit and the display coefficients; config_switch also enables snapping, disables smoothing and replaces labels; config_button enables snapping and disables smoothing and randomization, and leaves labels as your constructor set them. Anything else your __init__ sets (a description, display_precision, randomize_enabled) survives. Finally the Param takes the quantity’s default value. The call returns your object, and get_param_quantity and param_quantities return it again.

quantity_factories.py · Runs inside Rack; tested against the built plugin¶
from rackpy.engine import Module, ParamQuantity, SwitchQuantity


class Decibels(ParamQuantity):
    """Rack shows this label in the knob's tooltip and menu."""

    def __init__(self) -> None:
        super().__init__()
        self.description = "Output level."
        self.display_precision = 3

    def get_label(self) -> str:
        return self.name + " (dB)"


class Waveform(SwitchQuantity):
    def __init__(self) -> None:
        super().__init__()
        self.randomize_enabled = False  # config_switch keeps this


def describe(module: Module) -> None:
    module.config(num_params=2, num_inputs=0, num_outputs=0)
    module.config_param(0, -60, 6, 0, "Level", quantity_type=Decibels)
    module.config_switch(1, 0, 2, 0, "Wave", ["Sine", "Triangle", "Saw"], quantity_type=Waveform)


module = Module.create(describe)
try:
    level, wave = module.get_param_quantity(0), module.get_param_quantity(1)
    assert isinstance(level, Decibels) and level.get_label() == "Level (dB)"
    assert isinstance(wave, Waveform) and list(wave.labels) == ["Sine", "Triangle", "Saw"]
    assert wave.snap_enabled and not wave.randomize_enabled
    assert module.params[0].value == 0  # the Param starts at the default
finally:
    module.close()
assert not level.alive and not wave.alive

The ownership, retirement, error and reentrancy rules are those of metadata class factories: main thread only, alive becomes False and every member raises StaleHandleError once the slot releases the object, including a retained labels alias. Calls from Python keep the rules of attached quantities: value and display methods need Rack’s live bound UI context, and smoothing writes are refused until Rack’s engine owns the module (engine ownership).

Calls from Rack. A slot quantity is the one place in this API that Rack itself may call from another thread: Core’s MIDI-Map reads and writes mapped parameters from the engine thread. Those calls arrive without the GIL. They get Rack’s own native behaviour for the mixed value/range methods, never a Python call and never an exception into Rack. A UI-safe override that Rack calls on the main thread runs through RackPy’s contained dispatch: if it raises, Rack’s own answer is used. Mixed value/range overrides are refused when the class is defined, as for every Quantity; RP-22 owns their laboratory semantics. Rack’s model factory (RP-16) now creates RackPy modules and adds them to Rack’s engine; the test hooks also make such calls in the host tests.

Retiring an object hands it back to Python and may run its finalizer. An override that closes its own module leaves its object stale: the rest of that call raises StaleHandleError. Rack’s C++ API gives no protection against a callback deleting its own module, so do not do that in a callback Rack makes.

The three templates and get_param_quantity are implemented, and so is the raw paramQuantities vector (raw module vectors). For the ParamQuantity and SwitchQuantity records themselves, see what stays open.

Standalone quantities and weak module attachment¶

rackpy.engine.ParamQuantity and SwitchQuantity are aliases of the corresponding rackpy.raw.engine classes. They construct real, Python-owned SDK objects and inherit rackpy.raw.Quantity; a SwitchQuantity also inherits ParamQuantity. Constructing one does not install it in a Module slot; pass its class to a quantity class factory for that. Their mutable module field is a weak backreference: assigning a live RackPy Module preserves identity but neither retains that module nor transfers quantity ownership. Assign None to detach. When the module closes, construction rolls back or becomes unreachable, RackPy clears the native pointer and the quantity reads None. get_param() follows Rack’s raw semantics and returns the matching borrowed Param, or None for a null module or invalid param_id.

Attached value/display/helper/reset/randomize operations require a live bound Rack UI context and a valid parameter ID; invalid IDs are rejected before Rack’s unchecked vector access. Unattached values retain Rack’s null-module no-op/zero behavior. Smoothing writes to an attached quantity are refused unless Rack’s engine owns its module (engine ownership); use set_immediate_value() where the immediate semantics are intended.

Rack’s null-module semantics are important: these quantities do not store a value. get_value() and get_immediate_value() return zero, and native setters, reset and randomize do not change it. This also holds when smooth_enabled is true: with no module, Rack never reaches its engine. For a standalone quantity that actually stores a value, use rackpy.types.ValueQuantity instead.

The same scalar/text fields listed below for borrowed quantities are mutable, as is param_id (initially -1). Assigning fields does not initialize a Param. Raw equal/unbounded ranges retain SDK behavior. get_label() supplies Rack’s numbered default when name is empty. The maximum signed 32-bit param_id is storable, but requesting that default label raises ValueError rather than letting Rack overflow paramId + 1. Explicit names still work. Switch display strings reject nonfinite/out-of-int-range label indices before Rack’s cast.

Python subclasses may override the UI-safe virtuals get_display_value, set_display_value, get_display_precision, get_display_value_string, set_display_value_string, get_label, get_unit, get_string, reset, randomize, and get_description. Native virtual dispatch reaches those methods; super() reaches Rack’s implementation. Errors propagate to Python callers. Mixed value/range virtuals cannot be Python overrides in production: subclass definitions of get_value, set_value, get_min_value, get_max_value or get_default_value raise TypeError, like Quantity. RP-22 retains their explicit laboratory semantics. A standalone object is UI-only; only a class factory installs one in a Module slot.

All native access, construction and field operations require Rack’s main thread. Assigning a closed module or a non-Module value fails without changing an existing backreference. Closing or collecting a module clears the native pointer without keeping Python work on its teardown path; a quantity does not keep the module alive. Python code in an override is ordinary user code, not a sandbox or an audio callback. Inherited helper methods and direct base-class calls use the same native guards. Deprecated smooth-value methods emit DeprecationWarning. to_json() and from_json(data) are Rack’s; see Module JSON.

SwitchQuantity.labels uses the mutable SwitchLabels vector interface described below, including atomic conversion before assignment/extension and copied iteration. Unlike a borrowed module alias, an owned label alias keeps its standalone quantity alive. Its ownership edge is visible to Python’s garbage collector, so a subclass retaining its own label alias does not leak a cycle. Replacing the vector’s contents preserves retained aliases; deleting the alias eventually releases that ownership. This storage never enters the production audio path.

standalone_quantities.py · Runs inside Rack; tested against the built plugin¶
from rackpy.engine import ParamQuantity, SwitchQuantity
from rackpy.raw import Quantity
from rackpy.raw.engine import Module


class Captioned(ParamQuantity):
    def get_label(self) -> str:
        return super().get_label() + " (preview)"

    def get_description(self) -> str:
        return "An unattached quantity, not an engine parameter."


quantity = Captioned()
quantity.name = "Pitch"
quantity.unit = " V"
assert quantity.module is None and quantity.get_param() is None
quantity.set_value(0.75)  # Rack's null-module setter is a no-op, not value storage.
assert quantity.get_value() == 0

# A weak attachment gives Rack's getParam/value semantics without transferring
# this quantity into the module's engine-owned metadata slots.
module = Module.create(lambda m: m.config(1, 0, 0))
quantity.module = module
quantity.param_id = 0
assert quantity.module is module and quantity.get_param() is module.params[0]
# Attached value/display methods are only valid with a live bound Rack UI context.
quantity.module = None
module.close()
assert quantity.get_param() is None
assert Quantity.get_label(quantity) == ""  # explicitly Quantity's base implementation
assert quantity.get_string() == "Pitch (preview): 0 V"  # native getString dispatches to the label override
assert quantity.get_description().startswith("An unattached")

switch = SwitchQuantity()
switch.labels = ["Low", "High"]
labels = switch.labels
labels[0] = "Bass"
assert switch.get_display_value_string() == "Bass"
switch.labels = ["First", "Second"]
assert labels.tolist() == ["First", "Second"]
# An owned alias keeps its standalone quantity alive; borrowed module aliases do not.
del switch
labels.append("Third")
assert list(labels) == ["First", "Second", "Third"]

Built-in parameter quantities¶

config_param(param_id, min_value, max_value, default_value, name="", unit="", display_base=0, display_multiplier=1, display_offset=0) configures a built-in native ParamQuantity. config_switch(param_id, min_value, max_value, default_value, name="", labels=()) configures a native SwitchQuantity with snapping enabled and smoothing disabled. config_button(param_id, name="") uses bounds 0–1 and default 0, also disabling module randomization of the button. Each also accepts quantity_type (quantity class factories); without it, they configure the built-ins described here. All three helpers are constructor-only. Each writes the native Param’s default, prepares replacements before retiring old quantities, and invalidates only the replaced quantity view, not the Param component itself.

IDs are checked. Otherwise the helpers take what Rack’s take: infinite bounds (an unbounded quantity), equal or inverted bounds, a default outside them, and any display coefficients (a base of 1 or -1 gives infinite display values, as in C++). NaN is refused in the bounds, the default and the coefficients: every comparison with it is false, and Rack’s switch widgets and param menu convert value - min to an int, which is undefined for NaN. For the same conversion, a switch’s (config_switch, config_button) bounds and default must be finite and less than 2**31 apart.

get_param_quantity(index) and the fixed-size param_quantities collection return stable ParamQuantityView adapters (or SwitchQuantityView for switches and buttons). Rack’s config initializes every parameter’s quantity with bounds 0–1 and default 0; unlike light metadata, these slots are not initially null. Empty modules have empty collections. Negative indexing works only on the collection, not on getter/helper IDs. The views have no standalone constructor, no Python virtual trampoline, and do not inherit rackpy.raw.Quantity.

Quantity views expose these native scalar/text fields for reading and writing: min_value, max_value, default_value, name, unit, display_base, display_multiplier, display_offset, display_precision, description, reset_enabled, randomize_enabled, smooth_enabled, and snap_enabled. Direct field assignments, like C++, do not reset the Param or revalidate the whole range. Keep the metadata coherent; use the checked construction helpers for initial configuration. param_id and module can be assigned only during construction (module only the owner or None). get_param() returns the same checked Param as the owning module, or None for an ID out of range. alive remains a thread-independent liveness query. All other access requires the main thread. Replacement, failed construction, close and owner collection invalidate views; retaining a view does not keep the module alive.

Metadata methods get_min_value, get_max_value, get_default_value, get_display_precision, get_label, get_unit and get_description work without an engine. get_label() falls back to a numbered label for empty names.

Borrowed quantity helpers and switch labels¶

The views also expose Rack’s inherited Quantity helpers without pretending to inherit the standalone Python Quantity class. get_range(), is_bounded(), to_scaled(value) and from_scaled(scaled_value) work without an engine. They preserve Rack’s scaling rules, including equal bounds (scaled value 0) and unbounded ranges (identity conversion), and do not clamp conversion results.

SwitchQuantityView.labels returns a mutable SwitchLabels alias, not a copied list. Integer reads/writes/deletion, negative indices, insert, append, extend and clear operate on the native vector. Insertion clamps an out-of-range index as Python lists do; other indexed operations raise IndexError. Slicing is not supported. Assigning a complete string sequence to quantity.labels replaces the vector’s contents. A retained alias sees that replacement and remains valid across native vector reallocations. String conversion failures do not partially apply a replacement or extension.

labels.tolist() and list(labels) return independent copies. Iteration takes a snapshot when the iterator is created; that copied iterator remains usable after vector edits or owner deletion. Operations on the alias itself always check its quantity’s slot generation and main-thread rule. Replacing the quantity, failing construction, closing the module or dropping its final handle makes retained aliases stale. Label aliases do not keep the module alive. This adds borrowed vector editing, not standalone SwitchQuantity or full metadata-array mutation semantics.

Value/display methods require Rack’s live bound UI context. Calling them at plugin startup, or from a foreign context, raises ContextError rather than dereferencing a missing engine. They pin the module across GIL release and take a context teardown lease before calling Rack’s native implementation:

  • get_value / set_value, get_immediate_value / set_immediate_value;

  • get_display_value / set_display_value, get_display_value_string / set_display_value_string (including Rack’s expression parser);

  • reset and randomize; deprecated get_smooth_value / set_smooth_value aliases emit DeprecationWarning;

  • get_string, is_min, is_max, get_scaled_value, set_min, set_max, toggle, move_value, set_scaled_value and move_scaled_value. These are native Rack helpers, including switch snapping and formatted units.

Display scaling follows Rack: linear for base 0, exponential for a positive base, logarithmic for a negative base, then multiply and offset. Display writes are immediate, clamp to the range and respect snapping. Switch text lookup is case-insensitive; unmatched labels or invalid numeric expressions leave the value unchanged. Out-of-integer-range switch label indices raise ValueError before Rack’s float-to-int conversion. reset() / randomize() are direct quantity operations: the enable flags govern module-level reset/randomize, not these direct calls.

Smoothing needs Rack’s engine to own the module. Rack’s smoothing slot keeps a raw module pointer, which Rack clears only when it removes the module from its engine, so for a module Python owns, smooth_enabled=True is metadata only: set_value (and its deprecated alias), set_min, set_max, toggle, move_value, set_scaled_value and move_scaled_value then raise OwnershipError before changing any target. The helpers cannot bypass this guard by indirectly calling native setValue. set_immediate_value and display writes remain available. Once Rack’s engine owns the module, the same calls smooth as in Rack (engine ownership). No target is queued implicitly, and no Python callback runs on the audio thread.

Quantity records that stay open¶

The ParamQuantity and SwitchQuantity fields, UI virtuals (get_label, get_unit, the display methods, get_description), reset, randomize, get_immediate_value, set_immediate_value, get_param and both classes are implemented (RP-14B2b8): Python objects, slot-owned objects and built-in views give them their full semantics, including Python overrides of the UI virtuals.

get_value, set_value, get_min_value, get_max_value and get_default_value are mixed: Rack calls them from the engine thread as well (Core MIDI-Map). Their production path is native, and a subclass of ParamQuantity that overrides one is refused when it is defined. A Python override exists only in the laboratory (RP-22C): a subclass of rackpy.laboratory.ParamQuantity or SwitchQuantity, created after rackpy.laboratory.enable(), which only a laboratory module’s slots accept (an ordinary module’s raise LaboratoryError), so Rack’s engine thread never reaches it. Rack’s own code (display, reset, randomize, paramsToJson, paramsFromJson) then calls the Python methods synchronously on the main thread; see laboratory quantities. JSON (to_json, from_json) is RP-15.

Smoothing, including the deprecated set_smooth_value/get_smooth_value, works once Rack’s engine owns the module (RP-14C2) and is refused before.

Raw module vectors¶

Rack’s Module has eight public vectors: params, inputs, outputs, lights, and the owning pointer vectors paramQuantities, inputInfos, outputInfos and lightInfos. A plugin’s C++ constructor may edit them after config. RackPy maps that inside the constructor callback, after config: item assignment, del, insert, append, clear and resize(n) on the matching collection. Negative indices count from the end, insert clamps its position like list.insert, and other out-of-range indices raise IndexError.

  • Component vectors hold values. Assigning a Param, Input, Output or Light copies it into the slot, like C++ assignment; the source stays independent. resize adds default components. A structural edit (anything but item assignment) invalidates every view of that vector: Rack’s vector may have moved its storage, as with C++ iterators. Views of the other vectors stay valid.

  • Metadata vectors hold owning pointers. Assign a ParamQuantity (or SwitchQuantity), PortInfo or LightInfo you created, or None for a null slot. The module takes ownership, exactly as inputInfos[i] = info does in C++: no field is changed, so set module, the ID and the port type yourself. resize adds null slots. Built-in views, objects another slot owns and objects a slot has released are refused.

  • Removal releases. When a raw edit removes a pointer (assignment over it, del, clear, shrinking), Rack would not delete the object. A Python object comes back to you, still usable; if its module points at this module the link is tracked, so deleting the module later sets it to None. Built-in metadata has no other owner, so it is deleted and its views become stale. Replacement by a config_* helper and module deletion still delete, as in Rack.

raw_vectors.py · Runs inside Rack; tested against the built plugin¶
from rackpy.engine import Module, Port, PortInfo

def build(module: Module) -> None:
    module.config(num_params=0, num_inputs=2, num_outputs=0, num_lights=0)
    # Drop the second input, port and metadata together, as C++ would.
    del module.inputs[1]
    del module.input_infos[1]

    # assignment sets no fields, so set what the seal checks.
    info = PortInfo()
    info.module, info.port_id, info.type, info.name = module, 0, Port.Type.INPUT, "Clock"
    module.input_infos[0] = info
    # Add a light and an empty (None) metadata slot for it.
    module.lights.append(Light())
    module.light_infos.append(None)

finally:

The seal checks what Rack relies on. When the constructor callback returns, Rack’s own code (saving, reset, randomize, tooltips, the cable menu) assumes invariants it never checks. RackPy checks them and fails the construction with ValueError otherwise: each component vector matches its metadata vector in size; every parameter has a quantity and every port has metadata (light slots may be None); every object’s module is this module and its ID (and port type) matches its slot; every bypass route is inside the port vectors.

After the seal only item assignment to the component vectors remains: slot assignment and structural edits raise OwnershipError, and so do writes to the identity fields (module, the IDs and the port type) of any metadata a slot owns. Rack’s engine and UI index with those values unchecked. Every edit requires the main thread, and none is allowed before config. These eight records are implemented with this contract; bypassRoutes is RP-14C.

Ownership and failure¶

The returned handle owns its native module. Component/collection views do not keep it alive: closing or dropping the last module handle invalidates them. No pointer is exposed as an integer. close() is idempotent; alive tells whether the owned module remains. Reading a closed module or retained component raises StaleHandleError, never a use-after-free.

Calling close() during construction raises OwnershipError (a callback cannot delete the module out from under the factory). If the constructor raises, its original exception propagates and even escaped module/component handles are invalidated immediately. No half-constructed module can be published.

Construction, configuration, component access and explicit close require Rack’s main thread; Python worker threads get ThreadError. Dropping a final Python handle on another Python thread destroys the module there, with the GIL. Without class-factory metadata that runs no Python. Transferred metadata goes back to its Python object on that thread, so a finalizer of yours may run there. A module Rack’s engine owns is deleted by Rack instead; see below.

Engine ownership¶

In Rack, a module belongs to the engine once Rack adds it: Rack removes it from the engine and deletes it when its module widget goes, or at shutdown. RackPy implements Rack’s side of that (RP-14C2), which RP-16’s model factory uses; the test hooks also hand modules to the engine in the host tests.

  • Only a sealed module can go to the engine. Its id is then the one the engine assigned, and every handle and view stays valid, with the same identity.

  • close() raises OwnershipError: Rack deletes it. Dropping every Python handle does not delete it either, and Rack can hand it out again (as a module widget does), giving the same kind of handle.

  • When Rack deletes it, on its main thread without the GIL and after removing it from the engine, every handle, view and collection raises StaleHandleError (alive is False), and transferred metadata goes back to Python retired, taking the GIL for that alone. close() is then a no-op.

  • Smoothing writes are allowed, and smooth as in Rack: get_value returns the target at once and the engine moves the Param towards it.

Module JSON¶

Rack’s serialization methods are bound with Rack’s behaviour (RP-15A): to_json()/from_json(data) (the whole module; they need a registered model, RP-16), params_to_json()/params_from_json(data) (Rack’s live bound UI context), and data_to_json()/data_from_json(data), which reach the handlers set in the constructor callback with set_data_handlers(to_json=..., from_json=...). A ParamQuantity subclass may override to_json/from_json; Rack’s paramsToJson reaches the override. Values cross as ordinary Python data under the runtime’s JSON policy, never as a shared json_t. A module’s handle also reports its handlers and its slots’ transferred objects to Python’s garbage collector, so closures and subclass attributes that refer back to the module do not leak. Rules, threads and error handling are explained in save and restore a module’s state. Patch storage directories (get_patch_storage_directory, create_patch_storage_directory and the pathlib facade patch_storage()) follow Rack’s rules (RP-15B): an engine ID is required, and RackPy never deletes them.

Lifecycle events¶

Rack tells a module about its life through events: onAdd and onRemove (engine membership), onBypass/onUnBypass, onPortChange (a cable connected or disconnected), onReset and onRandomize (user commands), onSampleRateChange, onSave, onSetMaster/onUnsetMaster (which module drives the engine) and onExpanderChange (the module beside it changed). RackPy’s modules handle all twelve natively (RP-14C3; onExpanderChange since RP-22B): Rack’s own behaviour runs first (resetting or randomizing the parameters through their quantities, and calling Rack’s deprecated no-argument events), then RackPy records the event. No Python runs in these handlers apart from what Rack’s behaviour itself calls, such as a quantity subclass’s reset override, and that Python cannot take Rack’s engine lock (EngineLockError): the engine is locked exclusively for every event except onSave.

Observing events. module.lifecycle_events() returns the events since the last call, oldest first, as (sequence, event) pairs, where event is a copy of Rack’s own record: Module.AddEvent, Module.PortChangeEvent (with connecting, type and port_id), Module.SampleRateChangeEvent (with sample_rate and sample_time), Module.ExpanderChangeEvent (with side: 0 left, 1 right) and so on. This is RackPy’s API, not Rack’s: Rack may dispatch the sample-rate and master events on an audio driver thread, and expander changes on the thread stepping its engine, so recording takes no lock, allocates nothing and never calls Python, and Python reads the records later on the main thread. The queue holds 64 events; when it is full, a new event is dropped and counted in dropped_lifecycle_events. Sequence numbers count dropped events too, so a gap shows a loss.

Calling a handler. module.on_reset(Module.ResetEvent()) and its siblings call the module’s handler directly, as C++ plugin code may call Module::onReset(e). The module must be sealed and Python-owned, and Rack’s live bound UI context is required, because Rack’s behaviour writes parameters through the engine; the handler then runs exactly as when Rack dispatches it. For a module Rack’s engine owns, Rack dispatches the events, under its engine lock, and direct calls raise OwnershipError. The deprecated no-argument forms (on_reset(), on_add(), on_remove(), on_randomize(), on_sample_rate_change()) warn and dispatch the deprecated virtual, whose Rack implementation is empty and records nothing. A laboratory module can override that virtual separately, as described below.

Observing snapshots is not the same semantics as a synchronous Python handler. The UI-thread events have Python handlers (below); the sample-rate, master and expander events, which Rack may run on its audio threads, have Python overrides only in the laboratory.

Python handlers (RP-16C). set_event_handlers(on_add=..., on_remove=..., on_bypass=..., on_un_bypass=..., on_port_change=..., on_reset=..., on_randomize=..., on_save=...), in the constructor callback only, installs Python handlers that the adapters above call after Rack’s behaviour and the snapshot, on the main thread, with errors contained; rackpy.plugin.ModuleClass installs the methods a subclass overrides. See module events. model and get_model() are Rack’s: the module’s rackpy.raw.plugin.Model, or None for a module made directly with Module.create.

Laboratory events and JSON¶

Laboratory only

These overrides run only on a laboratory module, on an offline laboratory bench, after trusted code calls rackpy.laboratory.enable(). Rack’s engine never runs them.

A rackpy.laboratory.ModuleClass may override every event above (on_add, …, on_sample_rate_change, on_set_master, on_unset_master, on_expander_change) and Rack’s JSON virtuals: module_to_json and module_from_json (Rack’s Module::toJson and fromJson; named after Engine::moduleToJson, since ModuleClass.to_json is the custom-data handler), params_to_json, params_from_json, data_to_json and data_from_json. Unlike the handlers above, they are true overrides: called synchronously where Rack would call them, instead of Rack’s implementation, and super() runs it (Rack’s behaviour, RackPy’s snapshot, the data handlers). Rack’s own toJson calls the Python params_to_json and data_to_json, and fromJson the *_from_json ones. JSON overrides return JSON-compatible data, None for Rack’s NULL. Rack’s toJson and fromJson name the module’s model: ModuleClass.create(model) sets one, which only names it. The deprecated no-argument virtuals have separate overrides: on_add_legacy, on_remove_legacy, on_reset_legacy, on_randomize_legacy, and on_sample_rate_change_legacy. Defining one or explicitly calling its base implementation warns. Rack’s default modern handler calls the corresponding legacy override, without a warning just for that internal dispatch. A modern override that omits super() suppresses that dispatch. Direct module calls and bench callbacks propagate laboratory override errors to their Python caller. Details: laboratory modules.

Native kernels¶

set_kernel(kernel), kernel and kernel_failed are RackPy’s, not Rack’s: they give a module its production audio path, a native kernel that Rack’s engine runs from the module’s process() every frame. set_bypass_kernel(kernel), bypass_kernel and bypass_kernel_failed do the same for its processBypass() (bypass configuration). See processing audio. Rack’s process itself, as a Python override, exists only in the laboratory: see audio callbacks.

Audio callbacks: process, processBypass and step¶

Laboratory only

Rack’s engine threads call process, processBypass and the deprecated step() once per sample; RackPy never runs Python there. A rackpy.plugin.ModuleClass that defines them is refused. Their Python overrides run only offline, on a laboratory bench, after trusted code calls rackpy.laboratory.enable(); that is not real-time audio.

rackpy.laboratory.ModuleClass may override process(args), process_bypass(args) and step(); super() runs Rack’s implementations (process calls step(), processBypass copies the bypass routes, step() does nothing and warns as deprecated). Module.ProcessArgs is Rack’s argument record, a value with sample_rate, sample_time and frame. An ordinary module’s process is its native kernel, and its processBypass is Rack’s, or its native bypass kernel (set_bypass_kernel, below); a bench runs both, as Rack’s engine does. Details: laboratory modules.

Bypass configuration¶

config_bypass(input_id, output_id) validates both port IDs and refuses a second route to the same output with ValueError. An input may feed several outputs. Rack’s native processBypass preserves the routed channel count and voltages; the test-hooks build compares it against a standalone C++ reference for 0, 1 and 16 channels. Python reaches processBypass only through the laboratory’s ModuleClass.process_bypass, which is never on Rack’s audio path (laboratory modules).

Module.BypassRoute() is an independent value with mutable input_id and output_id, initially -1. module.bypass_routes is a checked collection of Rack’s route vector whose items are copies: changing a copy cannot corrupt routing. Inside the constructor callback, after config, it takes Rack’s raw vector edits like the other raw module vectors: item assignment of a BypassRoute, del, insert, append, clear and resize (new routes are (-1, -1)). A raw edit can create a second route to the same output, as C++ can; config_bypass still refuses that, as Rack’s configBypass asserts. The seal rejects routes outside the port vectors, and after it route edits raise OwnershipError, because Rack’s engine reads the routes while it processes a bypassed module.

When Rack’s engine owns the module and bypasses it, Rack calls processBypass instead of process: each route copies its input’s channels and voltages to its output. The live-UI tests drive this through cables in the real engine with 0, 1 and 16 channels and compare the output with Rack’s own processBypass on a plain module (RP-14C4). Enabling the module again clears its outputs, as Rack does.

set_bypass_kernel(kernel) replaces that route copy with a native kernel, RackPy’s equivalent of a C++ processBypass override (RP-34): Rack’s engine runs it for every bypassed frame with no Python, and the module’s ordinary kernel is not called. It is checked, handed over, reset, told about sample rate changes and silenced on failure exactly as set_kernel’s kernel; bypass_kernel returns it (or None) and bypass_kernel_failed reports a failure. A laboratory module refuses it with LaboratoryError: its bypass is its Python process_bypass. See process audio.

Expanders¶

Rack gives every module two expanders, leftExpander and rightExpander: the ID of the module next to it on that side, a pointer to that module, and two message buffers that the module allocates and Rack’s engine swaps when a flip is requested, so a message arrives one frame after it is written. In rackpy.raw.engine (and rackpy.engine.expanders):

  • left_expander, right_expander, get_left_expander(), get_right_expander() and get_expander(side) (0 is left, any other uint8_t right, as in Rack) return a Module.Expander view, on a RackPy module and on another plugin’s EngineModule. A view never owns the module; it raises StaleHandleError once the module is gone. Main thread.

  • module_id is the neighbour’s ID or -1. Rack sets it on the main thread for adjacent modules and when it loads a patch; Python may set it while Rack’s engine does not run the module.

  • module is the neighbour: its own Module handle if RackPy made it, an EngineModule otherwise, or None. It is read-only, because Rack’s engine sets the pointer from module_id at every block (through setExpanderModule, which is PRIVATE). While the engine runs the module, RackPy finds the neighbour by module_id through Rack’s engine instead of reading a pointer the engine thread writes.

  • producer_message and consumer_message are an ExpanderMessage, a ForeignMessage or None; message_flip_requested and request_message_flip() are Rack’s flag and request.

ExpanderMessage(schema, size) is a RackPy buffer of size float32 values (1 to 65,536), zeroed, under a schema name (1 to 64 letters, digits, _, . or -). It has schema, size, owner (the RackPy module whose expander holds it, or None), len(), indexing, tolist() and write(values). Assigning one to a slot of a RackPy module gives it to the module, which keeps it alive while a slot holds it; it can be in only one slot at a time, and the two slots of a side need the same schema and size, because Rack swaps them. allocate_messages(expander, schema, size) gives a side both of its buffers.

RackPy never shows Python a void*. It recognizes its own buffers by looking their address up in a registry, without reading the memory, so any other pointer, a foreign plugin’s, is an opaque ForeignMessage: it is true and compares equal to the same pointer, and is never read. Only a RackPy module takes RackPy messages; another plugin’s module allocates its own.

Rack’s engine thread reads, writes and swaps the message pointers and the flip flag while it runs a module, and Rack has no public way to pause it. So Python reads or assigns the slots, reads or writes a message’s values, and reads, sets or requests the flip only while Rack’s engine does not run the module: a Python-owned module, or one on a laboratory bench, which swaps requested buffers at the end of each frame as Rack’s engine does. Otherwise these raise OwnershipError. Exchanging messages in production, one sample apart, is native code’s work: DSP graphs send and receive lanes of "rackpy.graph" messages (graph expanders, graph_messages(expander, lanes)), checking on Rack’s engine thread, without locks, that the neighbour is a RackPy module whose messages fit.

expanders.py · Runs inside Rack; tested against the built plugin¶
from rackpy import laboratory
from rackpy.engine import Module
from rackpy.engine.expanders import ExpanderMessage, allocate_messages
from rackpy.laboratory import Bench

    bench = Bench(48000)

    bench.add(neighbour)

Snapshots. While Rack’s engine runs a module, Python sees what native code receives through snapshots instead: set expander.snapshots = True (at any time, on a RackPy module) and expander.snapshot() returns (frame, values), a consistent copy of the message as native code received it in that frame, or None before the first. Native code copies it at most once per frame, before marking anything read, and only while snapshots are on; a sequence lock keeps the copy whole, so Python may read it while Rack’s engine thread writes. Snapshots exist for RackPy messages that native code receives (graph nodes and kernels through rackpy/expanders.hpp).

Native code. DSP graphs exchange lanes of "rackpy.graph" messages (graph expanders), and C++ kernel libraries exchange messages under schemas of their own through RackPy’s expander services (from C++), which check the neighbour, its back link and the buffers without locks or reading foreign memory. That contract is how a void* message gets a meaning in RackPy: for RackPy buffers, from their schema, in Python and in native code alike; for another plugin’s pointer, only from native code that checks that plugin’s model, as Rack prescribes. Python never reinterprets a foreign pointer.

Established: Rack’s own engine delivers each message exactly one frame later at 44.1, 48 and 96 kHz with 1, 2 and 4 engine threads, in both graph tiers and for a library’s own schema; removal, reordering and a schema mismatch give silence; Python reads whole snapshots while Rack’s engine thread runs; and a stress run of hot removal, insertion, reordering, foreign and mismatched neighbours, snapshot toggling and concurrent snapshot reads is clean under AddressSanitizer, UndefinedBehaviorSanitizer, LeakSanitizer and ThreadSanitizer (Rack’s engine reproduced, libRack not instrumented).

The native test injects a preparation exception to verify replacement rollback. Quantity tests also cover 1,000 slot replacements and 1,000 owner collections, stale getters/setters, thread/context rejection, validation rollback, native display/label/value comparisons, reset/randomize and unsafe smoothing rejection. Borrowed-helper and label tests add native differential helper replay and edited label lookup, mutable alias/snapshot behavior, 1,000 alias replacements and owner collections, conversion failure atomicity, degenerate scaling and indirect smoothing refusal. The offline bypass dispatch hook is test-only.

With the test hooks playing Rack’s part, the live-UI suite also has Rack’s engine own modules: adoption and Rack-side deletion (1,000 times), engine smoothing, every lifecycle event Rack dispatches (add, remove, bypass, sample rate, master, save, cable port changes, and a seeded reset and randomize equal to a plain Rack module’s), a raising override contained inside an event, engine-lock refusal inside exclusive events, bypass routing through cables with 0, 1 and 16 channels, and Rack’s own save and reload of a configured module, which restores parameter values and bypass while the constructor rebuilds scales, labels and routes. The lifecycle adapters’ object references no CPython (bin/rackpy-dev audio-symbols).

Not established: an audio driver thread actually dispatching sample-rate or master events. The tests use no audio device, so that path is known from Rack’s source and the Python-free object only. As in Rack, a module widget’s module is None in the module browser’s previews. Per-platform results are recorded by CI in release-evidence/, not on this page.
