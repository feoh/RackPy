ADR 002: Embedding CPython and choosing a binding library¶

  • Status: Accepted for Linux x86_64 on the evidence below. macOS and Windows have concrete risk probes only; nothing has run there.

  • Date: 2026-10-21

  • Task: RP-04

  • Evidence: spikes/embedding, tests/integration/test_embedding_smoke.py

Context¶

RackPy runs inside Rack. It has to load a Python runtime from a Rack plugin, own that interpreter safely, and expose Rack objects whose lifetimes Rack controls. The pinned Rack source (src/plugin.cpp at 061ccf63) and the spike established these facts about the host:

  • Rack opens each plugin library with dlopen(RTLD_NOW | RTLD_LOCAL), and calls dlclose after destroy() at shutdown.

  • /tmp/Rack2 (the plugin RUNPATH that finds libRack) exists only while Rack’s own dlopen runs. Rack removes it again before calling init().

  • A plugin whose manifest names a module that init() did not register is rejected, and Rack never calls its destroy().

  • Standalone Rack calls init() before it creates the Context (contextGet() is NULL). Modules and module widgets are created on the main thread with a context. At shutdown Rack deletes them while tearing down the scene, then the engine, and only then calls plugin destroy().

  • A patch that references an unavailable module makes Rack show a blocking osdialog message, even in headless mode.

The spike ran in Rack Free 2.6.6, Linux x64, headless (Rack -h -u <dir>) with python-build-standalone 20261021 (CPython 3.14.9 and 3.15.1, install_only). The test runs these scenarios, all passing (10 passed, about 50 s on the planning machine):

The deciding difference: who frees a Python subclass¶

Rack frees widget children, menu items and modules with plain delete. A Python subclass handed to Rack therefore needs C++ heap storage that lives as long as C++ wants, and its Python state has to survive until then.

  • pybind11 3.1.0 (py::classh with trampoline_self_life_support): the C++ object is separate from the Python object (storage inside python object=False). attach() takes a std::unique_ptr<Widget> and gives it to Rack’s tree. on_add ran through the trampoline. At shutdown Rack’s delete ran on_remove, then released the Python object (its __del__ ran) on the main thread, before Py_FinalizeEx. No crash.

  • nanobind 3.1.0: the C++ object lives inside the Python object (storage inside python object=True), and nanobind refuses the transfer: “could not transfer ownership of a Python instance of type ‘spike_plugin.Child’ to C++”. Its alternative, std::unique_ptr<T, nb::deleter<T>>, frees with Py_DECREF rather than delete, so it cannot be handed to Rack either. Supporting Rack ownership would need a C++-allocated proxy object at every API that takes ownership.

Decisions¶

  1. Two-stage loading. plugin.so is a thin loader with no Python dependency. It checks for another interpreter, verifies the bundled runtime, opens libpython with RTLD_NOW | RTLD_GLOBAL | RTLD_NODELETE, then opens the host library with RTLD_NOW | RTLD_LOCAL | RTLD_NODELETE. The loader and host talk through a C ABI (host_api.h). Every DSO links libstdc++ statically, so no C++ exception or RTTI crosses that boundary.

  2. Bundled, relocatable CPython. Each artifact ships one python-build-standalone install_only runtime in <plugin>/python. The loader never uses a system Python.

  3. Python ABI. Start with CPython 3.14, the full (not limited) ABI, with the GIL (not the free-threaded build). 3.15.1 passed the same tests and is the next candidate; adding it is a per-artifact rebuild. 3.14 goes first because it has been out a year longer. Its scheduled end of life is 2030-10.

  4. Interpreter ownership. RackPy owns the only interpreter in the process. The loader refuses to start when any libpython is already mapped (dl_iterate_phdr also sees libraries other plugins opened RTLD_LOCAL) or Py_IsInitialized() is true. A refused plugin registers no models. Subinterpreters are not used.

  5. Isolated configuration. PyPreConfig_InitIsolatedConfig with UTF-8 mode and PyConfig_InitIsolatedConfig with: home set to the bundled runtime, no site, no user site, no bytecode writing, no Python signal handlers, no C stdio changes and no argv parsing. sys.path is the plugin directory plus the bundled standard library. Errors are reported, never passed to Py_ExitStatusException, which would exit Rack.

  6. Thread and lifetime rules shown by the spike (RP-06 extends them): initialize in init() on the main thread, then release the GIL; callbacks take it with PyGILState_Ensure; finalize in destroy(), after Rack has deleted every module and widget. If host init fails, the loader finalizes immediately because Rack will not call destroy().

  7. Binding library: pybind11 3.1.0. Every Rack type that Python may subclass and Rack may free uses py::classh and a trampoline derived from trampoline_self_life_support. nanobind is not used: it was smaller and faster to build here, but it cannot give Rack ownership of Python subclasses. The spike is too small to say how compile time scales to the whole API; RP-07 and RP-08 measure that and may split translation units.

  8. Borrowed Rack objects. Python holds a shared token, never the Rack pointer. Deleting a module only clears an atomic flag. Later access raises ReferenceError. The production process() path makes no Python calls.

  9. Code provenance. The host imports only trusted scripts shipped inside the plugin directory. Patch files never run code.

Linux loading rules¶

  • Loader: SDK flags, RUNPATH /tmp/Rack2, exports init and destroy only.

  • Host: built with -fvisibility=hidden; exports rackpy_spike_host_init, rackpy_spike_host_destroy and the module init function. RUNPATH /tmp/Rack2:$ORIGIN/python/lib. Its NEEDED libRack.so resolved to the libRack Rack had already loaded, even after /tmp/Rack2 was gone.

  • libpython3.14.so.1.0 is found by explicit path, not by search.

  • RTLD_NODELETE on libpython and the host keeps them mapped after Rack dlcloses the loader, so no static destructor runs after finalization.

macOS and Windows: risks to probe natively¶

Evidence gathered on Linux from the pinned installers, not from running them:

  • macOS. The Rack Free app is a universal x86_64 + arm64 binary. Its embedded entitlements include com.apple.security.cs.disable-library-validation, allow-jit and allow-unsigned-executable-memory, so library validation should not block a separately signed libpython. RP-40 must check: -undefined dynamic_lookup together with an RTLD_GLOBAL libpython for extension modules; @loader_path install names; quarantine attributes on extracted .vcvplugin contents; ad hoc versus Developer ID signing of every bundled .dylib and .so; and both architectures natively.

  • Windows. libRack.dll and Rack.exe import msvcrt.dll, and Rack ships its own libstdc++-6.dll, libgcc_s_seh-1.dll and libwinpthread-1.dll. CPython’s official Windows builds use MSVC with the UCRT, so the process would contain two C runtimes. Windows LoadLibraryW does not search the plugin directory for dependencies, which the two-stage loader handles by loading python3XY.dll by full path (LoadLibraryExW with LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR). RP-41 must prove that a MinGW-built host can use an MSVC-built python3XY.dll with no CRT objects (FILE*, malloc) crossing, or choose a different runtime build.

Blockers and alternatives¶

There is no blocker for Linux x64. If Windows cannot mix runtimes safely, the alternatives are a MinGW-built CPython (as MSYS2 builds it) or an out-of-process design. The out-of-process option would contradict the in-process owner decision and needs owner review.

Consequences¶

  • RP-06 builds on this lifetime model. It must test the GIL against Rack’s engine lock when a widget is deleted while Python holds the GIL; every trampoline destructor acquires it.

  • RP-08 scaffolds the loader/host split, the bundled runtime and pybind11 3.1.0 pins. It also needs an old-glibc toolchain for distributable builds.

  • RP-10 implements the context policy above.

  • The runtime adds about 252 MB unpacked before trimming. RP-39 ships it without Tcl/Tk, _dbm, pip and ensurepip, with its shared libraries stripped: 126 MB unpacked. With rackpy_host.so (46 MB, stripped) a Linux plugin is about 173 MB unpacked and 48 MB as a .vcvplugin (licensing).

  • Windowed Rack, macOS and Windows remain untested. No support is claimed for them.
