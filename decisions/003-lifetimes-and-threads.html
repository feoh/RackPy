ADR 003: Thread affinity, lifetimes and callback semantics¶

  • Status: Accepted for Linux x64 Rack Free 2.6.6 on the evidence below. Audio-driver-thread paths are known from source only (no audio device in the tests). Rack Pro multi-instance hosting is unsupported.

  • Date: 2026-10-21

  • Task: RP-06

  • Evidence: spikes/lifecycle, tests/integration/test_lifecycle_probe.py, callback matrix, upstream/callback-rules.json

How the evidence was gathered¶

  1. Read the pinned Rack source (061ccf63) for every place that constructs, deletes or calls back into modules and widgets, and every lock each engine method takes.

  2. Ran a probe plugin in Rack Free 2.6.6 with a window (inside Xvfb), in screenshot mode and headless. It logs the thread role of every callback and measures whether audio processing continues while a callback runs.

  3. Classified all 434 public virtual methods from the RP-05 inventory with reviewed rules. bin/callback-matrix check fails if any is unmatched.

tests/integration/test_lifecycle_probe.py passes 7 tests in about a minute.

What Rack does¶

The engine lock¶

The engine has one SharedMutex (Engine::Internal::mutex).

Measured: while onReset ran (exclusive), process() advanced 0 samples in 30 ms. While dataToJson ran (shared), it advanced 800. Saving therefore runs concurrently with audio; edits stop it.

Other facts:

  • contextGet() is thread-local (context.cpp:48). Engine workers and driver callbacks set it themselves. A thread Python creates has none: the probe’s worker saw has_context=False.

  • ModuleWidget::~ModuleWidget calls setModule(NULL), which runs engine->removeModule (exclusive) and then delete module, both on the main thread.

  • Browser previews and screenshots construct widgets with createModuleWidget(NULL) and step and draw them. The probe confirmed this.

  • ContextCreateEvent and ContextDestroyEvent fire only when the window is constructed or destroyed (window/Window.cpp:369, 378). Rack 2.6.6 standalone never re-creates its window at runtime (that code is commented out in adapters/standalone.cpp). onContextDestroy reaches widgets at shutdown, before they are deleted.

  • At shutdown ~Context deletes, in order, the window, patch manager, scene (and with it every module widget and module), event state, history and then the engine. Plugin destroy() runs after all of that. Rack gives plugins no “context closing” callback.

Decisions¶

Thread rules¶

  1. No Python on engine or driver threads in production. Every Rack-to-Python dispatch goes through one helper that refuses (and counts) calls from engine threads. Across every probe run, GIL acquisitions on engine threads were 0.

  2. Every binding that can take the engine lock releases the GIL first. The probe proved why. A Python thread that kept the GIL while waiting for the shared lock deadlocked against a Python onReset override that Rack ran under the exclusive lock. A watchdog killed it after 30 s. With the GIL released, the same worker made 17 million locking calls during 200 such callbacks with no deadlock. RP-11’s binding manifest records locks_engine for each engine method from the lock table above, and the generator emits gil_scoped_release for them.

  3. Engine calls are refused inside exclusive-lock callbacks. SharedMutex is not recursive, so a locking engine call from inside onReset would deadlock its own thread. RackPy marks the thread while it dispatches an ui-exclusive callback, and such calls raise RuntimeError instead. The probe confirmed the refusal.

  4. Engine calls from Python threads scope the bound context. They set it for the duration of the call and restore the previous value.

  5. Python runs only inside the strategy its callback allows. See the matrix:

Ownership and lifetime¶

  1. Rack-owned objects are borrowed through tokens. Modules, widgets in Rack’s tree, cables, the engine and the context are never owned by Python. A handle holds a shared token. Deletion flips an atomic flag and does no Python work. Later use raises ReferenceError. In the stress run, all 40 deleted modules’ handles raised it from a Python thread, alongside 1.9 million valid reads.

  2. Python-created objects that Rack will own are transferred. Widgets and menu items use pybind11 py::classh with trampoline_self_life_support (ADR 002). Rack frees them with delete on the main thread; the trampoline then releases the Python object under the GIL.

  3. Python-owned values are copies. Vec, Rect, colours and snapshots own their storage; buffers keep it alive.

  4. Identity. One Python wrapper per live Rack object, keyed by (pointer, token generation), never by address alone, because addresses are reused. Implementation: RP-10.

  5. Scoped views. Wrappers for DrawArgs, events, the menu passed to appendContextMenu and the JSON passed to dataFromJson are valid only during the callback and raise afterwards. Implementation: RP-10, RP-25.

  6. Strong references. C++ keeps registered Python callables alive with strong references and drops them before finalization. Every py::object must be gone before Py_FinalizeEx: in the probe, a local py::dict that outlived it crashed Rack at exit (SIGSEGV in _Py_Dealloc).

Context and teardown¶

  1. One bound context. RackPy binds the first Context it sees, which the first module constructor provides (plugin init() runs before the context exists). Python work for any other context is refused until RP-10 adds context-generation tokens. Multi-instance hosts are unsupported until then.

  2. Teardown ordering. All of these steps are tested:

    1. RackPy attaches a sentinel widget to the scene. Its destructor during scene deletion is the teardown signal, windowed or headless, and comes before the engine is deleted. Amended in RP-28B (2026-10-26): the windowed signal was the sentinel’s onContextDestroy, but Rack saves its autosave after deleting its window, and the patch needs the Python module widgets (module positions, cables) and the modules they own. The window’s onContextDestroy still releases graphics resources.

    2. There, RackPy calls Python to stop and join its worker threads.

    3. It then takes its own lease exclusively, so in-flight engine calls from Python finish, and marks the context dead. Later calls raise ReferenceError.

    4. Rack deletes modules and the engine. Module deletion flips tokens only.

    5. Plugin destroy() invalidates handles, lets Python clean up, drops every strong reference and calls Py_FinalizeEx (which returns 0).

  3. No window re-creation. Rack 2.6.6 standalone does not re-create its window, so GL resources (fonts, images, framebuffers) are released on onContextDestroy and never rebuilt. A host that does re-create the window would send onContextCreate again; RackPy will rebuild caches lazily, but that path is untested.

State and queues (designed, measured in RP-07)¶

  1. Synchronous JSON adapters. dataToJson calls Python on the UI thread and converts its result before returning, as Rack requires; the probe did this. dataFromJson hands Python the JSON while audio is stopped. Neither defers work; a deferred answer is not equivalent.

  2. Bounded queues; the audio thread never waits. UI-to-engine changes go through a fixed-capacity single-producer, single-consumer ring that process() drains without locking; overflow coalesces or drops and is counted. Engine-to-UI notifications (expander changes, sample-rate changes, driver events) go into a ring or a double-buffered snapshot that a UI-thread step drains into Python. Only atomics were exercised here; RP-07 measures the queue design, and RP-14, RP-17 and RP-21 implement it.

Consequences and blocked work¶

  • RP-10 implements the bound context, generation tokens, identity registry, scoped views, the sentinel and the lease.

  • RP-11 adds locks_engine and the callback strategy to every manifest entry, and fails generation for an engine-locking binding without gil_scoped_release.

  • RP-14 must keep ui-exclusive Python short and refuse engine re-entry. RP-13/RP-14 implement Quantity value and range methods natively.

  • RP-22 owns every engine callback’s Python laboratory path.

  • RP-29 resolved the 31 driver and device methods (amended 2026-10-26). They are driver: Rack calls them from driver threads and the engine thread, and Core Audio reads Device::getNumInputs and getSampleRate in processInput on the audio thread. Python may implement drivers and devices only as natively configured objects. Native code answers every call from values Python set, Python drives the streams from its own thread, and Rack’s requests reach Python as queued UI-thread notifications (planning/rp-29-slices.md).

  • RP-07 must set the ui-exclusive time budget and measure the queues.

Not covered¶

  • Audio and MIDI driver threads were not exercised: the tests use no audio device, to avoid touching the machine’s sound system. Their rows come from source.

  • Rack Pro, DAW hosting and multiple contexts are untested and unsupported.

  • macOS and Windows are untested.
